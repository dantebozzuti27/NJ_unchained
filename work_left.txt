(migration 051) + L3a scoring function (migration 052) + Read API +
CLI + UI + Dagster wiring (asset + 3 asset checks) shipped. The
analyst queue lands at /fraud, is query-able via
  GET /fec/risk/entities?cycle=2024
  GET /fec/risk/entities/{kind}/{id}
  GET /fec/risk/entities/{kind}/{id}/csv
or as `nj-terminal fec-risk` / `fec-risk-entity`. Dagster auto-refreshes
L1 whenever raw.fec_candidate or raw.fec_committee materializes;
attached asset checks surface (a) empty L1 when cn is loaded, (b)
missing signal_ids from a silently-broken refresher, (c) L3a returning
score=0 for everyone when L1 has data. Triage workflow (L5) and the
unsupervised / supervised score layers (L3b, L3c) are gated on
production analyst-label volume, not engineering. Inverts the v2.A
model (eight flat per-signal lists) to an entity-first risk score with
multi-signal fusion, peer-group normalization, and a transparent
evidence trail.

Why redesign
------------
The user reviewed v2.A and asked for an engine that "surfaces potential fraud,
gives a % prediction, and backs it up with data." Two design pressures
follow from that ask:

  (a) v2.A is a CATALOG of eight lists. There is no entity-level synthesis,
      no fusion across signals, no peer-group context. A committee that
      fires on three signals at the 99th percentile is buried in three
      separate tabs alongside thousands of mild flags.

  (b) "% probability of fraud" requires labels we do not have at scale.
      Real enforcement actions (FEC RAD MURs, DOJ filings) produce on the
      order of dozens of NJ-relevant labels per cycle vs. tens of thousands
      of entities. A naive probability would be a confidently wrong
      number that an opposing lawyer ends the platform with on cross.

Honest framing: the user-facing scalar is a RISK SCORE (0-100), defined as
the entity's percentile of anomalousness within its peer bucket, NOT a
probability of fraud. A real `P(fraud | features)` field appears only after
the L5 triage queue produces enough analyst-confirmed labels to fit and
calibrate (isotonic) a held-out classifier. Until then the API field is
`risk_score_pct`, not `p_fraud`.

Five-layer architecture
-----------------------
L5  Triage workflow      analyst queue (sorted desc by risk_score) ->
                         confirm / reject / escalate; writes weak labels
                         + feature snapshots to governance.fraud_review
L4  Evidence panel       per-entity drill: score decomposition (which
                         signals contributed how many points), per-signal
                         raw rows, 5-NN peer comparison, network sub-graph
                         for relational signals
L3  Scoring engine       L3a rule-based weighted score (ship first;
                         transparent baseline)
                         L3b unsupervised anomaly score (IsolationForest /
                         Mahalanobis per peer bucket); ship second
                         L3c calibrated supervised classifier (only after
                         labels exist); ship last
L2  Entity feature store wide format keyed on entity; one row per
                         (cycle, entity_kind, entity_id) with the L1
                         observations pivoted to a feature vector
L1  Signal layer         long format observations:
                         (cycle, entity_kind, entity_id, signal_id,
                          raw_value, severity, peer_bucket, peer_percentile,
                          evidence_url, materialized_at)
                         Existing 8 v2.A signals slot in unchanged via
                         adapter; Tier-B relational signals are additive.

Entity kinds are first-class: 'committee', 'candidate', 'treasurer',
'address', 'donor_cluster'. Treasurer requires promotion (currently a
string column on cmte) via a canonicalization pass + a new derived.
fec_treasurer table -- without it, treasurer signals cannot have peer
percentiles.

L1 schema (proposed)
--------------------
  CREATE TABLE derived.fraud_signal_observation (
      cycle           CHAR(4)   NOT NULL,
      entity_kind     TEXT      NOT NULL,
      entity_id       TEXT      NOT NULL,
      signal_id       TEXT      NOT NULL,
      raw_value       NUMERIC,
      severity        SMALLINT  NOT NULL,   -- 1..5 ordinal, analyst-curated
      peer_bucket     TEXT      NOT NULL,   -- 'office=H|state=NJ|incumbent=challenger'
      peer_percentile NUMERIC   NOT NULL,   -- 0.0..1.0 within bucket
      evidence_url    TEXT      NOT NULL,
      materialized_at TIMESTAMPTZ NOT NULL,
      PRIMARY KEY (cycle, entity_kind, entity_id, signal_id)
  );

Two non-obvious design choices:

  * peer_percentile, NOT raw value, is what L3 consumes. Senators have more
    donors than House challengers; their address clusters are larger.
    Without peer-group normalization a senator looks "fraudulent" because
    they're big. Default bucket: (office, state, incumbency_class), with
    fallback to (office, state) when bucket size < 30.

  * severity is analyst-curated, not learned. A self-treasurer flag
    (severity 1) is qualitatively weaker evidence than a transfer cycle
    (severity 4). Encodes domain priors until labels arrive; under L3c
    these become Bayesian priors that get updated, not magic numbers.

L3a scoring formula (proposed)
------------------------------
  raw_sum(entity) = SUM_s phi(percentile_s, severity_s)
  phi(p, sev)     = sev * max(0, p - 0.95)^gamma
  score(entity)   = 100 * (1 - exp(-k * raw_sum))
  gamma           = 2
  k               = 50    -- tunable; calibrate against analyst-confirmed cases

Properties:
  * raw_sum = 0  -> score = 0          (no signals fired -> no risk)
  * raw_sum -> +inf -> score -> 100    (extreme stack of high-sev tail signals)
  * monotone in each (severity, percentile) pair
  * smooth (no kinks); percentile rank on score = percentile rank on raw_sum

Why NOT sigmoid: sigmoid(0) = 0.5, so 0 inputs -> score 50. That breaks the
"no signals fired => no risk" invariant. exp(-k*raw_sum) form has the
right zero-input semantics and the same bounded, monotone shape.

Tail-only contribution: a 60th-pct signal is "normal", not "lightly
suspicious". Squaring the tail makes the score insensitive to noise below
threshold and sensitive to extreme outliers. Additive fusion is deliberate:
multiplicative ("AND") fusion explodes when 3+ signals fire and is
indefensible in court. Print the formula on the evidence panel.

k=50 calibration check (sanity, not ground truth):
  * one signal at sev=3, p=0.99: raw_sum = 3*(0.04)^2 = 0.0048
                                  -> score ~ 21
  * five signals at sev=5, p=1.0: raw_sum = 5*5*(0.05)^2 = 0.0625
                                  -> score ~ 96
  * single sev=5 at p=1.0:        raw_sum = 5*(0.05)^2 = 0.0125
                                  -> score ~ 47
Re-tune k once we have an analyst-confirmed reference distribution.

Architecture (v2.A delta)

db/migrations/040_fec_metrics_structural.sql
  8 derived.fec_* views. All cycle-scoped. Each row carries a
  severity_score column on a uniform [1, 1000] scale so the UI can
  rank signals consistently. Canonicalization (REGEXP_REPLACE upper +
  whitespace collapse) catches "PO BOX 99" / "P.O. BOX 99" /
  "P O BOX 99" as one address. Views, not materialized tables --
  cn/cm are 10K-21K rows so per-query cost is < 50 ms total.

db/migrations/041_relax_fec_indiv_amt_check.sql

  MetricSpec dataclass + _METRIC_CATALOG dict. get_catalog() returns

Architectural choices made today
---------------------------------
* SHARED APP, SEPARATE BUNDLE. One nj-serve process serves both UIs +
  both API surfaces (housing /burden/*, fraud /fec/*). Same DB pool,
  same observability middleware, same lifespan. The two UIs are
  separate HTML+JS bundles only.

* SERVER-SIDE FILTERING + PAGINATION. The UI never holds a full
  result set client-side. limit + offset go to the API; total_count
  comes back in a FecPagedResponse envelope so the UI renders
  pagination controls without a second /count round trip. A Tabulator-
  client-only table would have crippled the contributions tab once
  raw.fec_contribution holds the full ~25M-row indiv24 dataset.

* STREAMING CSV EXPORTS WITH SERVER-SIDE NAMED CURSORS. Each export
  uses conn.cursor(name=...) which streams from Postgres in itersize
  chunks; the FastAPI generator yields one CSV line at a time; the
  client gets Transfer-Encoding: chunked. Memory stays flat regardless
  of result set size. 100k row hard cap for safety; documented in the
  X-Export-Cap-Rows response header so callers can detect truncation.

* SORT WHITELIST = DEFENSE IN DEPTH. Every endpoint has an explicit
  per-table dict of sortable columns. An attacker passing
  sort_by='1; DROP TABLE raw.fec_candidate' silently falls back to
  the first whitelisted column rather than 4xx-leaking that the
  column doesn't exist (or worse, getting a parameter through to
  Identifier()). Pinned by unit test.

* EMPTY-STRING FILTERS ARE NOT PREDICATES. UI dropdowns set value=""
  for "all"; the WHERE-clause builders MUST treat that as "no
  predicate", not as `col = ''` (which would silently return zero
  rows). Pinned by unit test test_build_candidate_where_skips_empty_
  string_filters.

* PYDANTIC RESPONSE MODELS = OPENAPI CONTRACT. Every endpoint declares
  a response_model so /openapi.json carries the full schema. Frozen
  models prevent post-construction mutation (DTO discipline).

* CSS [hidden] OVERRIDE. The detail-panel uses display: flex when
  open; HTML's `hidden` attribute is overridden by that and would
  fail to hide the panel. .detail-panel[hidden] { display: none; }
  restores intent (caught by browser smoke test, not by unit tests).

TIER 4 CHECKPOINT v1 (2026-04-29 EVE) -- FEC BULK INGESTER, END-TO-END
================================================================================
The platform now has its first civic-integrity ingester. FEC bulk data --
the canonical free source for federal candidates, committees, and itemized
individual contributions -- is stateless, idempotent, vintaged, queryable,
and wired into Dagster with five asset checks.

Why FEC first
-------------
FEC is the unique data source that simultaneously satisfies:
  * Stable entity backbone (FECID; 9-char, 18 years of stability) that
    other Tier 4 datasets join into (PACs that hire lobbyists in
    Senate LDA; PACs that get federal contracts in USAspending; donors
    that show up in NJ ELEC + FEC for state/federal stacking).
  * NJ axis is first-class (cand_office_st='NJ' yields 257 candidates
    for the 2024 cycle, validated live 2026-04-29).
  * Bulk-downloadable, no auth, S3-backed (Accept-Ranges: bytes,
    ETag-stable), so conditional GET works.
  * Time series back to 1980 (we ingest current-cycle by default).
  * Dollar amounts in every contribution row -- fraud signal substrate.

Tables
------
raw.fec_candidate    -- Candidate Master (cn{yy}.zip), PK (cycle, cand_id)
raw.fec_committee    -- Committee Master (cm{yy}.zip), PK (cycle, cmte_id)
raw.fec_contribution -- Individual Contribs (indiv{yy}.zip), PK sub_id
                        (large; ~25M rows for a presidential cycle)

Canonical views (public.v_*)
----------------------------
v_fec_candidate                  -- typed pass-through
v_fec_committee                  -- typed pass-through
v_fec_contribution               -- MMDDYYYY -> DATE; is_memo flag
v_fec_nj_candidates              -- cand_office_st='NJ' slice
v_fec_money_to_nj_candidates     -- HEADLINE: contributions to NJ-
                                    candidate committees, joined three
                                    deep (contrib + committee + nj cand)

Architectural choices made today
---------------------------------
* RAW MIRRORS SOURCE BYTES. transaction_dt stays as 8-char MMDDYYYY in
  raw; cooking happens in public.v_fec_contribution. No row drops on
  malformed dates -- we coerce to NULL with COALESCE and CASE so the
  raw -> view path is total.

* SUB_ID IS THE PK ON raw.fec_contribution. Per FEC docs sub_id is
  globally unique. cycle is denormalized into the row (not part of
  PK) for partition-friendly query plans; DELETE WHERE cycle=%s
  before COPY guarantees idempotent re-load.

* QUOTE_CHAR=NONE FOR FEC PARSING. Real FEC bulk contains literal
  double-quote characters in plain text fields ('JOHN "JACK" DOE',
  '"VAL" VALMA PAUL'). Polars's default quote_char='"' aborts on
  these. Setting quote_char=None disables CSV quote interpretation
  entirely, matching FEC's actual unquoted byte format. Pinned with
  test_parse_handles_literal_double_quote_in_name regression test.

* COPY ... FROM STDIN WITH (FORMAT csv, DELIMITER '|', QUOTE E'\b').
  The bell-character QUOTE escape disables Postgres's CSV quote
  interpretation while keeping FORMAT csv's empty-field-as-NULL
  semantics. Matches the FEC byte format byte-for-byte and lets us
  stream the 4.2 GB indiv24.zip directly from a zipfile.open() into
  COPY without ever materializing the contents in Python memory.

* MEMO_CD='X' DOUBLE-COUNT HAZARD HANDLED. The is_memo column in
  v_fec_contribution flags itemized sub-line entries; the headline
  view exposes the flag and downstream summable analytics filter
  WHERE NOT is_memo. COALESCE(memo_cd='X', false) so NULL memo_cd
  is False, not NULL (otherwise WHERE NOT is_memo would drop the row
  -- 3-valued logic trap caught by integration test).

PRIOR CHECKPOINT (v4 historical) -- VARIANCES, NOT JUST POINTS
===================================================================================
Every PUMS-derived percentile in the platform now ships with a
Census-methodology standard error. Both segmented burden tables --
PUMA grain and county grain -- expose three new SE columns
(household_income_p50_se, monthly_cost_p50_se, burden_ratio_p50_se)
alongside their point estimates. The shift is conceptual:

    Before: GET /pums-burden-county/34003 -> Bergen renter burden 0.294
    After:  GET /pums-burden-county/34003 -> Bergen renter burden 0.294
                                            (90% CI = [0.290, 0.298])

That difference is the line between "the API returns numbers" and
"the API returns statistics."

Why this matters for the BBG mental model
------------------------------------------
The platform invites comparison by design ("Hispanic renter burden vs
white renter burden"). Without standard errors, those comparisons are
unfounded -- a consumer cannot distinguish a structural inequality
finding from sampling noise in a thinly-sampled demographic group.
With SDR-based SEs:

  * Demographic subgroup cells (smaller samples) automatically show
    wider CIs than overall baselines (verified live: 0.0036 for
    citizenship subgroups vs 0.0023 for overall renter baseline in
    Bergen).
  * Cells whose CIs overlap can be flagged "no significant
    difference" before they are presented as a finding.
  * A future UI can render error bars without re-deriving variances
    on the client.

Methodology: Successive Differences Replication
------------------------------------------------
ACS PUMS publishes 80 replicate weights per record; the Bureau's SDR
estimator is:

    Var(theta_hat) = (4/80) * sum_{r=1}^{80} (theta_hat_r - theta_hat)^2

We apply it directly to weighted percentiles (recompute the q-quantile
under each replicate weight) and to the burden ratio (recompute the
ratio of two percentiles per replicate -- NOT delta-method). The
ratio-of-replicates approach is critical: cost_p50 and income_p50
share their weight column, so the joint replicate distribution
captures their covariance for free; delta-method would assume
independence and underestimate the SE.

For multi-county PUMAs the replicate weights are first multiplied by
the PUMA-county allocation factor, so the SE for a Salem cell sourced
partly from PUMA 02501 correctly reflects both within-PUMA sampling
variance and the additional fractional-allocation uncertainty.
Single-county PUMAs (allocation = 1.0) degenerate to the standard SDR.

NULL-handling rules
-------------------
* Suppressed cells (weighted_n < 1000): all SE columns NULL alongside
  the NULL p50.
* Cell where the sanity-cap fired (ratio > 5.0): all p50 + SE NULL,
  marked suppressed.
* Cell where fewer than 40 of 80 replicates produced a finite estimate
  (extreme low-info case): SE is NULL even though the point is
  populated. The 50% threshold is configurable; below it, the variance
  estimate is biased low and reporting it would be misleading.

Architectural decisions
-----------------------
1. **One generic SDR primitive, not per-statistic.** Both
   `weighted_percentile_sdr` and `ratio_of_percentiles_sdr` live in
   `derived/_stats.py` next to the existing weighted-percentile
   primitive. Adding SE for a new statistic (e.g. weighted mean wage)
   is a one-function change, not a per-aggregator rewrite.

2. **SE, not CI, in the table.** A CI is a function of (theta, SE,
   alpha). Storing SE leaves alpha to the consumer; storing CI fixes
   it at materialization time. Mirrors how Census itself publishes
   ACS estimates (tables ship with 90% MOEs but the underlying SE is
   what's analytically useful for hypothesis testing).

3. **Schema additions, not new tables.** ALTER TABLE ADD COLUMN with
   nullable defaults means the migration applies clean against
   existing rows; the next materialization populates the new columns.
   No data backfill required.

4. **Compute cost: ~80x.** Each cell's percentile is now computed 81
   times (once main, 80 times replicate). For NJ at 1-year vintage
   (~500 cells) this is ~40s vs. the prior ~500ms. Acceptable for an
   annual materialization. Could be vectorized (multiply 80 replicate
   columns into a single matrix and percentile per column) if we ever
   need 5-year or multi-state.

5. **Two new asset checks.** standard_errors_non_negative on each
   PUMS-derived table -- the principal guard on the variance pipeline.
   SE is sqrt(variance) by construction; a negative value means a
   numerical regression. Easy to express, hard to lie to.

THE METHODOLOGICAL POINT THAT MATTERED
----------------------------------------
Naive design: roll up `derived.pums_burden_segmented` (PUMA grain) to
counties via the crosswalk by averaging the medians.

Why we did NOT do this: median-of-medians is statistically invalid.
Two PUMAs with median income $50K and $80K do NOT have a combined
median of $65K. To recover a true county median you need the raw
distribution, weighted by allocation.

What we did instead: the derived.pums_burden_county_segmented
materialization re-aggregates from raw PUMS through the crosswalk.
For each PUMS person, allocate PWGTP = (raw weight) x (allocation
factor) to each county the person's PUMA spans, then compute a
weighted percentile across all county-allocated observations. For
single-county PUMAs (allocation = 1.0), this degenerates to the
PUMA-grain compute. For multi-county PUMAs, each observation
contributes fractionally to multiple counties. Cost: ~2x the PUMA
table compute time (~1s for NJ at 1-year vintage). Gain:
statistically defensible numbers.

A live smoke test confirmed the invariant: PUMA 02501 contributed
weighted_n = 3200 renters at PUMA grain. After 0.56/0.44 county
split, Salem received 1792, Cumberland received 1408. Sum = 3200.
Allocation conserves population.

Architectural decisions
-----------------------
1. **First multi-grain derived analytical table.** The PUMA and
   county tables are siblings, not parent-child. Both compute from

Architectural decisions
-----------------------
1. **First materialized derived TABLE in the platform.** Every prior
   derived asset is a SQL VIEW. PUMS-derived stats break that pattern
   because computing weighted percentiles across ~100K rows x ~30
   cells is expensive (~500ms per cell) but the output is small (~4K
   rows). Materialize once per refresh, serve cheap SELECTs at read.

2. **Long-format segmentation schema.** One row per
   (puma, year, tenure, segment_dim, segment_value) rather than
   wide columns per dimension. Adding a new segmentation (e.g.
   educational attainment, language at home) is a compute-side
   change only -- no migration. Cost: ~3x row count vs. wide; the
   data is small enough that it doesn't matter.

3. **PUMA grain, not county.** PUMS reports PUMA. Pre-aggregating
   to county at materialization would lose precision and would
   require a PUMA-county crosswalk that doesn't exist yet. We expose
   the precise PUMA grain; consumers who want county can compose
   later.

4. **Methodology: ratio-of-medians, not median-of-ratios.** The
   cell's burden ratio is `median_cost*12 / median_income`, NOT the
   median of per-row burden ratios. This matches HUD/Census
   published methodology and is robust to top-coded incomes (PUMS
   replaces top 0.5% income with state median above the cap).
   A property test in tests/test_pums_burden.py
   (test_burden_ratio_uses_ratio_of_medians_not_median_of_ratios)
   constructs a pathological case where the two diverge and asserts
   we use the right one.

5. **Suppression at weighted_n < 1000.** Mirrors ACS Detailed Tables
   disclosure-avoidance threshold. Cells below the floor have NULL
   ratios and `suppressed=TRUE`. Default API behavior excludes
   suppressed cells (consumers must opt in via
   `?include_suppressed=true`); the rationale is that suppressed
   cells with NULL ratios are easy to misread as "this group is not
   burdened."

6. **Sanity cap at burden_ratio = 5.0.** Any cell whose computed
   ratio exceeds 5.0 is coerced to suppressed. Real burdens above
   5.0 are virtually always artifacts of $1-coded near-zero income
   or divide-by-zero. The threshold is documented as a constant in
   derived/pums_burden.py and tested.

7. **AutomationCondition.eager() on the derived asset.** When EITHER
   raw.acs_pums_person OR raw.acs_pums_housing materializes, the
   Dagster daemon queues a re-materialization within ~30s. An
   architectural-contract test in tests/test_orchestration.py
   asserts the derived asset depends on BOTH raw assets, so a
   regression where one is dropped from `deps=` would fail in CI.

TIER 3 CHECKPOINT (2026-04-29 late morning, eighth pass) -- PUMS LIVE
======================================================================
The platform now has person-level microdata. ACS PUMS 1-year for NJ
loads via `nj-ingest-pums` and is registered as two Dagster assets
(`raw.acs_pums_person`, `raw.acs_pums_housing`) with annual freshness
policies and four quality gates.

Why this matters
-----------------
Every other table in the platform is an aggregate -- one row per
(county, year). Aggregations answer "is Bergen burdened?" but they
CANNOT answer the platform's headline product question:

    "Are Hispanic renters in Bergen aged 25-34 burdened more than
     white renters? More than non-citizens? More than 5 years ago?"

That question requires person-level microdata with proper sampling
weights. PUMS provides it. With this load, the platform's analytical
surface area expands from ~21 county aggregates to ~100K NJ persons
per year, segmentable on:

  * Race (RAC1P: 9 categories)
  * Hispanic origin (HISP: 24 origin codes)
  * Citizenship (CIT: 5 categories incl. naturalized vs non-citizen)
  * Nativity (native vs foreign-born)
  * Age (AGEP: 0-99)
  * Sex
  * Educational attainment (SCHL: 24 levels)
  * Employment status (ESR)
  * Class of worker (COW)
  * Tenure (TEN: owned-w-mtg, owned-no-mtg, rented, no-rent)
  * Income (WAGP, PINCP, HINCP, FINCP)

Crucially, all queries against PUMS MUST weight by PWGTP (persons)
or WGTP (households). Standard errors require the 80 replicate
weights. These are stored as Postgres `INTEGER[]` arrays per row.

Architectural decisions (substrate-shaping)
-------------------------------------------
1. **PUMS is a sample, not an aggregate.** This is the first table
   that violates the "1 row per (geography, year)" assumption. The
   asset checks include a `replicate_weights_cardinality_80`
   invariant precisely because a row with fewer than 80 weights
   would silently produce wrong standard errors -- a class of
   error the platform's previous gates couldn't catch.

2. **PUMA, not county.** PUMS reports geography at the Public Use
   Microdata Area level (~100K population). PUMA boundaries do
   NOT align with county boundaries; allocation lives in the
   derived layer (TODO: PUMA-county correspondence migration)
   and uses Census's geographic correspondence files. We do NOT
   pre-allocate at ingest time so the original PUMA precision
   is preserved for queries that need it.

3. **DELETE + COPY, not UPSERT.** PUMS occasionally republishes a
   vintage with corrections; the natural-key shape (year, product,
   serialno, sporder) is too wide for a sensible UPSERT. DELETE
   the prior vintage's rows, COPY the new ones, all in a single
   transaction. Idempotent and atomic.

4. **Replicate weights as INTEGER[], not 80 columns.** Cleaner
   schema, identical query performance, and `cardinality()`
   makes the "must be exactly 80" invariant a one-line CHECK.

5. **One fetch, two COPYs, two assets.** The PUMS person and
   housing files are published as a paired drop. We fetch them
   together (a single helper, `_materialize_pums_pair`) but
   register them as TWO assets so the asset graph mirrors the
   database schema. raw.acs_pums_housing depends on
   raw.acs_pums_person to express "the housing COPY happens
   during the person asset's compute."

PRODUCT MENTAL MODEL                                                  [GUIDING]
==============================================================================
This is NOT a research notebook, a one-off dashboard, or an analyst report.
It is a "Bloomberg Terminal for civic + housing data": a continuously
updated, vintaged, queryable, alertable single-source-of-truth that
answers "what is this number, AS OF when, FROM where, and how has it
moved" for every series the platform tracks.

What that mental model demands (and what we have not yet built):

  1. EVERY DATASET HAS A KNOWN RELEASE CALENDAR.
       Bloomberg's ECO <GO> screen tells you "BLS CPI for May releases
       2026-06-12 08:30 ET, prior 2026-05-15." We need:
         * release_calendar table keyed by (source_id, expected_date)
         * sensor that detects late releases ("BLS CPI is 3 days stale")
         * sensor that auto-runs the loader within minutes of release

  2. EVERY CELL HAS AN AS-OF TIMESTAMP, SURFACED.
       We have ingested_at + source_sha256 per row. The UI/API must
       expose them so the consumer always knows freshness.

  3. ALERTS, NOT JUST QUERIES.
       Bloomberg's BIG <GO> news alerts; portfolio threshold alerts.
       For us: "Hudson owner burden ratio crossed 50% in latest ACS5",
       "USAspending NJ vendor X concentration >70% with single agency",
       "FHFA HPI revision changed 2023 by >2% for any NJ county."

  2. fastexcel/calamine renders integer-valued numeric cells as "1.0",
     which Postgres' COPY rejects against INTEGER columns. Loader now
     splits _NUMERIC_COLS into _FLOAT_COLS + _INT_COLS with explicit
     round+cast for the integer path.

       - 2018 LCA form: EMPLOYMENT_START_DATE -> BEGIN_DATE,
                        EMPLOYMENT_END_DATE   -> END_DATE,
                        TOTAL_WORKERS         -> TOTAL_WORKER_POSITIONS

     v3/v4/v5 mappings + v5 signature were silently using the old
     names; live data therefore landed with NULL employment dates +
     NULL NAICS until corrected. Per-vintage mappings now diverge
     explicitly and date columns are no longer in `_BASE_V2PLUS`.
